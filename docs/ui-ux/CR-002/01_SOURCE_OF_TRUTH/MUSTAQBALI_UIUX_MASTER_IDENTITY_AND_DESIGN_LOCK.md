## 1. قاعدة المرجع الأعلى لهذا التصميم

من الآن، أي تصميم جديد للمنصة يجب أن يبدأ من هذا الملف ومن الصور المرجعية المعتمدة المدرجة في قسم **المراجع البصرية** أدناه.

### ممنوع الرجوع إلى
- أي هوية سابقة لا تستخدم شعار **مستقبلي** المعتمد.
- أي تصميم استخدم رمز الريال كشعار للمنتج.
- أي تصميم استخدم IBM Plex Sans Arabic.
- أي اتجاه داكن عنابي / فاخر / Paris-style منفصل عن الهوية.
- أي Sidebar أو Navigation مختلفة بصريًا عن اللغة المعتمدة في Board 01 وBoard 02.
- أي ألوان عشوائية أو تدرجات غير ناتجة عن هوية مستقبلي.
- أي تصميم يشبه بوابة بنك تقليدية، منصة تداول، نظام حكومي، أو جمعية.

إذا تعارض تصميم مولد لاحقًا مع هذا الملف، **يُرفض التصميم المولد ويُعاد إنتاجه**؛ ولا يتم تعديل هذا المرجع ليتبع التصميم المولد.

# 2. جوهر العلامة التجارية

## الاسم
**مستقبلي**

## Brand Descriptor
**إدارة أذكى لحياتك المالية**

## الفكرة
مستقبلي ليس سجل مصروفات فقط، بل منصة إدارة مالية شخصية تساعد المستخدم على:
- معرفة وضعه المالي بسرعة.
- معرفة ما يستطيع إنفاقه بأمان.
- تنظيم الحركة المالية.
- التخطيط للميزانية والالتزامات والأهداف.
- اكتشاف المخاطر والفرص مبكرًا.
- الحصول على تحليل وتوصيات تساعد على اتخاذ القرار.

## الشخصية
- ذكية.
- هادئة.
- واضحة.
- موثوقة.
- شخصية وليست مؤسسية ثقيلة.
- حديثة لكن غير استعراضية.
- إيجابية وموجهة للمستقبل.

## الوعد البصري
المستخدم يجب أن يفهم الشاشة **من النظرة الأولى** عبر:
**مؤشر → معنى → أولوية → إجراء**.

# 3. الشعار الرسمي

الشعار المعتمد هو الشعار الهندسي الذي يجمع:
- شكلًا هندسيًا صاعدًا.
- أعمدة / نمو مالي.
- سهمًا أو اتجاهًا للأعلى داخل الرمز.
- كلمة **مستقبلي**.

## النسخ المسموحة
1. الشعار الرئيسي: الرمز + كلمة مستقبلي.
2. الرمز فقط للتطبيق/Favicon والمساحات الصغيرة.
3. نسخة أفقية عند الحاجة.
4. نسخة أحادية اللون فقط لضرورة التباين أو الإنتاج.

## قواعد حاسمة
- **رمز الريال السعودي ليس الشعار.**
- رمز الريال يستخدم للمبالغ المالية فقط.
- لا يتم إعادة رسم الشعار من تلقاء المصمم في كل Board.
- لا تغيّر نسبه، هندسته، ألوانه أو وضعه من Board إلى آخر.
- تحسين الشعار مستقبلًا مسموح كـRefinement مستقل، وليس أثناء تصميم الصفحات الحالية.

# 5. الخط Typography

## الخط الوحيد المعتمد للواجهة
**Tajawal**

IBM Plex Sans Arabic ملغى لهذا التصميم.

## الأوزان
- Regular 400 — نصوص ومحتوى.
- Medium 500 — Labels / metadata المهمة.
- Bold 700 — العناوين والقيم الرئيسية.

## الاتجاه
- Arabic RTL first.
- الأرقام المالية واضحة وثابتة.
- العناوين قوية ولكن **غير ضخمة**.
- لا نستهلك أعلى الشاشة بعنوان كبير؛ يجب أن يبدأ المحتوى سريعًا تحته.

## مبدأ التسلسل
1. Page Title.
2. Primary financial value / decision metric.
3. Section title.
4. Card title.
5. Supporting text / Meta.

# 6. رمز العملة

رمز الريال الذي زوده المستخدم هو **Asset مالي فقط**.

يستخدم في:
- الرصيد.
- الدخل.
- المصروف.
- الميزانية.
- الالتزامات.
- الأهداف.
- التحويلات.
- التقارير.

قواعد الاستخدام:
- أصغر بصريًا من الرقم.
- بمحاذاة ثابتة مع خط الأرقام.
- لا يستخدم كترويسة أو شعار أو Watermark.
- الأولوية دائمًا لسهولة قراءة المبلغ.

# 9. حقول الإدخال والنماذج — Mobile Priority

هذه القاعدة مهمة جدًا في تصميم مستقبلي.

## المشكلة التي نعالجها
منع النماذج الطويلة التي تستخدم حقلًا واحدًا في كل صف بدون ضرورة.

## قاعدة الهاتف
الافتراضي هو **Adaptive 1–2 Columns**.

### حقلان في صف واحد عندما تكون القيم قصيرة
أمثلة:
- المبلغ + التاريخ.
- التصنيف + النوع.
- الحالة + الأولوية.
- من حساب + إلى حساب إذا كانت التسميات مختصرة.
- مدينة + منطقة.

### Full Width
- الوصف.
- الملاحظات.
- البحث.
- النص الطويل أو المتغير.
- أي حقل تصبح قراءته سيئة عند تقسيمه.

### ممنوع
- 3 أعمدة في الهاتف كقاعدة عامة.
- ضغط المحتوى فقط لتقليل الطول.

الهدف:
> **أقل Scroll ممكن مع أعلى وضوح، وليس أعلى كثافة بأي ثمن.**

# 10. Page vs Modal / Bottom Sheet على الجوال

## Page First
أي Workflow رئيسي يصبح **صفحة كاملة**.

أمثلة:
- إنشاء ميزانية جديدة.
- إنشاء خطة.
- إضافة عملية مالية رئيسية.
- تعديل ميزانية كاملة.
- رحلة متعددة الخطوات.

## Modal / Bottom Sheet فقط للإجراء الفرعي
أمثلة:
- إضافة بند داخل ميزانية موجودة.
- تعديل بند بسيط.
- اختيار تصنيف.
- فلتر.
- تأكيد حذف.
- اختيار حساب.

### قاعدة التحويل إلى صفحة
إذا أصبح الـBottom Sheet يحتوي على:
- أقسام متعددة، أو
- خطوات، أو
- Scroll طويل، أو
- نحو 5 حقول فعلية أو أكثر مع منطق واضح،

فهو لم يعد إجراءً فرعيًا ويجب تحويله إلى **Page**.

# 11. Card Anatomy

أي بطاقة تحتوي على بيانات وحالة وتاريخ وإجراء تُبنى دائمًا كالتالي:

1. **Header** — Icon / Title / Status.
2. **Content** — القيمة أو المعلومة الأساسية.
3. **Meta** — التاريخ، التصنيف، المصدر.
4. **Actions** — عرض التفاصيل / الإجراء.

## ممنوع
- دخول الزر بين النص والتاريخ.
- تداخل CTA مع محتوى البطاقة.
- فرض ارتفاع ثابت يترك فراغًا أو يسبب قصًا.

**Card height = content driven.**

# 13. الرسوم والمؤشرات

لا نستخدم نفس نوع الرسم لكل البيانات؛ **نوع الرسم يتبع السؤال الذي نريد الإجابة عنه**.

| المعلومات | التمثيل المفضل |

| تقدم هدف | Progress bar / Ring |
| الالتزامات القادمة | Rings / concise indicators / timeline عند الحاجة |
| الدخل مقابل المصروف | Grouped bars |
| التدفق النقدي عبر الزمن | Line / Area / Bars حسب المقارنة |

| اتجاه زمني | Line / column trend |

قاعدة Dashboard:
**المؤشر السريع أولًا، التفاصيل عند الطلب.**

# 14. Desktop vs Mobile

Desktop وMobile تجربتان مستقلتان ضمن نفس الهوية.

## Desktop
- يستفيد من المساحة بحرية.
- يمكن استخدام 3–5 أعمدة حسب المحتوى والمساحة.
- لا نطبق عليه قيود كثافة الهاتف.
- Sidebar قابلة للطي.

## Mobile
- الأولوية للقابلية للمسح السريع.
- تقليل vertical scroll غير الضروري.
- max 2 columns للمدخلات القصيرة.
- Tables تتحول إلى Cards / lists منظمة.
- الإجراءات الرئيسية Pages؛ الفرعية Bottom Sheets/Modals.

# 15. Information Hierarchy — قاعدة كل شاشة

كل شاشة يجب أن توضح في أقل وقت ممكن:

1. **أين أنا؟**
2. **ما أهم معلومة الآن؟**
3. **هل هناك خطر أو شيء يحتاج انتباه؟**
4. **ما الإجراء الأقرب؟**
5. **أين التفاصيل إذا احتجتها؟**

Dashboard hierarchy:
**وضعك الآن → ما يحتاج انتباهك → الإجراء الأقرب → الخطة والتقدم → الحركة الأخيرة → التفاصيل.**

10. لا تعتبر أي صورة مولدة اعتمادًا نهائيًا إذا كانت النصوص أو الهوية انحرفت.
