# UX_ARCHITECTURE.md

## نظام إدارة الميزانية الشخصية والمستشار المالي

---

# 1. الهدف من الوثيقة

تحدد هذه الوثيقة:

* خريطة المنصة.
* الهيكل المعلوماتي.
* الصفحات الرئيسية.
* محتوى كل صفحة.
* الإجراءات الرئيسية.
* التسلسل اليومي للاستخدام.
* تجربة الجوال.
* تجربة الكمبيوتر.
* حالات Loading / Empty / Error.
* الأولويات البصرية والمعلوماتية.

هذه الوثيقة لا تحدد بعد:

* الألوان.
* الخطوط.
* أشكال البطاقات.
* المسافات الدقيقة.
* التصميم البصري النهائي.

يتم ذلك لاحقًا في:

```text
DESIGN_SYSTEM.md
```

---

# 2. المبدأ الأساسي لتجربة المستخدم

النظام ليس دفتر مصروفات.

النظام يجب أن يتصرف مثل:

```text
Personal Financial Command Center
+
Financial Advisor
```

ولذلك يجب أن تجيب تجربة الاستخدام باستمرار عن أربعة أسئلة:

```text
أين ذهبت أموالي؟
كم أستطيع أن أصرف الآن؟
هل وضعي المالي يتحسن أم يتراجع؟
ماذا يجب أن أفعل بعد ذلك؟
```

---

# 3. UX Principle — Action Before Data

لا تعرض البيانات لمجرد العرض.

كل معلومة رئيسية يجب أن تؤدي إلى:

```text
فهم
أو
قرار
أو
إجراء
```

لذلك لا تصبح الصفحة الرئيسية مجموعة رسوم بيانية ضخمة.

بل مركز قرار مالي.

---

# 4. UX Principle — Safe To Spend First

أهم رقم تشغيلي للمستخدم ليس:

```text
Account Balance
```

بل:

```text
Safe To Spend
```

لذلك يجب أن يحصل:

```text
Safe To Spend
```

على أولوية أعلى من الرصيد البنكي في الصفحة الرئيسية.

---

# 5. UX Principle — One Primary Action

كل شاشة رئيسية يجب أن تمتلك إجراءً رئيسيًا واضحًا واحدًا قدر الإمكان.

مثال الصفحة الرئيسية:

```text
إضافة عملية
```

أو حسب السياق:

```text
تسجيل الراتب
اعتماد الخطة
تسجيل مصروف
```

الإجراء الرئيسي يتغير حسب حالة الدورة.

# 13. Dynamic Primary Action

يتغير الزر الرئيسي حسب حالة النظام.

## لا توجد دورة

```text
بدء دورة مالية
```

## دورة DRAFT

```text
إكمال الخطة
```

## دخل متوقع لم يسجل فعليًا

```text
تسجيل نزول الراتب
```

## خطة غير معتمدة

```text
مراجعة واعتماد الخطة
```

## دورة فعالة

```text
إضافة عملية
```

## قرب نهاية الدورة

يمكن إظهار:

```text
مراجعة الدورة
```

ولا يتم إغلاق الدورة تلقائيًا من الواجهة.

# 15. Forecast Block

يعرض:

```text

```

مثال:

```text

```

أو:

```text
يوجد عجز متوقع بقيمة 740 ريال
```

---

# 16. Upcoming Obligations

```text

250 ريال

```

```text

```

# 17. Advisor Card

# 24. تعديل الميزانية

إذا كانت الخطة:

```text
PLAN_DRAFT
```

يسمح بالتعديل مباشرة.

إذا كانت:

```text
ACTIVE_PLAN
```

يجب أن يكون الإجراء:

```text
تعديل الخطة
```

ثم إنشاء Revision وليس تغيير القيمة الأصلية بصمت.

# 119. Definition of UX Integrity

تعتبر تجربة المستخدم سليمة إذا:

* يستطيع المستخدم معرفة Safe To Spend فورًا.
* يستطيع تسجيل مصروف بسرعة.
* لا تختلط القيم الفعلية بالمتوقعة.
* لا تختلط المبالغ المخصصة بالمبالغ المحولة فعليًا.
* لا يستطيع تنفيذ انتقال State غير مسموح.
* لا يعتقد أن الرصيد البنكي كله قابل للصرف.
* كل توصية يمكن تفسير سببها.
* لا تنفذ توصية مالية دون موافقة المستخدم.
* الجوال ليس نسخة مصغرة من Desktop.
* كل شاشة تمتلك إجراءً واضحًا.
* حالات Empty / Loading / Error مصممة.
* لا تضيع البيانات التاريخية بسبب تصميم الواجهة.

# 120. قاعدة الحوكمة

أي شاشة جديدة يجب أن تجيب عن:

```text
ما هدف الشاشة؟
ما السؤال الذي تجيب عنه؟
ما الإجراء الرئيسي؟
ما البيانات الضرورية؟
ما البيانات الثانوية؟
ما State التي تؤثر عليها؟
ما Business Rule المرتبطة؟
ما حالة Empty؟
ما حالة Loading؟
ما حالة Error؟
كيف تعمل على Mobile؟
كيف تعمل على Desktop؟
```

إذا لم توجد إجابات واضحة، فلا تتم إضافة الشاشة.
